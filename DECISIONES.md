# Decisiones

**Diseño del prompt.** El system prompt ([`prompt.py`](app/classifier/prompt.py)) le da al modelo el contexto de Pitz (marketplace B2B, áreas que escriben, Brasil/México) y define cada categoría, prioridad y área con una frase; esas listas se generan desde los enums, así que prompt, esquema JSON y validación nunca divergen. La prioridad usa literalmente el criterio del enunciado. Incluye dos ejemplos completos (mensaje → respuesta): el del Anexo B y uno **inventado en portugués**, que agregué cuando un test detectó resúmenes a medio traducir ("planilha de vendas…"). El mensaje va entre `<mensaje>` y se indica que su contenido nunca son instrucciones (defensa básica contra prompt injection). La salida se fuerza con JSON schema y además se valida con Pydantic (20 palabras, coherencia `requiere_info`/pregunta); si falla, se reintenta **reenviando el error al modelo**, porque con `temperature = 0` repetir el mismo prompt daría la misma respuesta.

**Dónde duda o se equivoca.** MSG-05 (HubSpot) salió como `consulta`/`devops`; lo veo como bug de integración (`data`/`backend`), aunque es ambiguo a propósito. MSG-12 mezcla una consulta ("¿cómo proceso el reembolso?") con un bug de pagos (3 cobros duplicados): eligió bug/alta, que comparto. La prioridad de MSG-02 (cierre contable con plazo) y MSG-04 (2 h diarias manuales) es discutible entre media y alta/baja. Además: marca `requiere_info` en 9 de 12 mensajes (demasiado preguntón) y a veces encadena 2-3 preguntas aunque se le pide una. Ojo: el acierto en **MSG-01 no prueba nada**, porque es el ejemplo del prompt.

**Cómo mediría en producción.** (1) Un set de evaluación etiquetado a mano (estos 12 sin MSG-01 + casos reales), con exactitud por campo, corrido en cada cambio de prompt o modelo. (2) La señal más valiosa: **cuántas clasificaciones corrige el equipo** (reasignar área, cambiar prioridad), guardando la corrección para ampliar el set. (3) Operativas: tasa de respuestas inválidas/reintentos, latencia, % de `requiere_info` y si los solicitantes responden la pregunta. Empezaría en *shadow mode* (sugerencia visible, decisión humana).

**Costo.** Medido con los 12 mensajes: ~1.870 tokens de entrada y ~105 de salida por mensaje. Con Haiku 4.5 (USD 1 / 5 por millón) son **≈ USD 0,0024 por mensaje → ≈ USD 1,2 por mes con 500 solicitudes**; aun triplicándolo por reintentos queda bajo USD 4. Cerca del 75 % del costo es el system prompt, que es igual en todas las llamadas, así que prompt caching o el Batch API lo bajarían más, aunque a este volumen no se justifica la complejidad.

**Datos sensibles.** Implementado: antes de llamar al LLM se enmascaran CNPJ, CPF, RFC, emails y tarjetas (`MASK_SENSITIVE_DATA`); solo se envía el mensaje y el área, y la API key vive en `.env`. Faltaría: nombres y teléfonos (no se enmascaran), revisar con Legal la retención de datos del proveedor y un acuerdo de procesamiento (LGPD en Brasil, LFPDPPP en México), no loguear mensajes crudos, control de acceso a la base (hoy no hay login) y cuidar que la pregunta de seguimiento no pida datos sensibles (en MSG-08 pidió CNPJs).

**Con dos semanas más.** (1) **Integración con Slack** (slash command o webhook → respuesta en el hilo), que es donde nacen las solicitudes. (2) Set de evaluación + corrección de la clasificación desde la web, cerrando el ciclo de feedback. (3) Notificar al canal del equipo asignado y detectar duplicados (MSG-12 ya habla de "tres casos así"). (4) Docker, login y ajustar el prompt para que pregunte menos y una sola cosa.
